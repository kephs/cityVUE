[ADR-027 — Platform Operator Bootstrap and Recovery](ADR-027-platform-operator-bootstrap-recovery.md): **Accepted** (2026-10-04). Records the accepted architecture for establishing and recovering privileged production administration: no bootstrap token, with authority coming from existing infrastructure/deployment authority through a production-mode operator CLI; platform operator as a principal concept separate from Organization-bound tenant staff, so tenant RBAC cannot manufacture platform authority; control-plane versus tenant data-plane separation as a security boundary; recovery bounded to restoring a trusted identity to already-authorized authority; no local authentication fallback; and infrastructure authority acknowledged as the trust root. Isolated deployment-per-tenant first. **Documentation only — acceptance authorizes no CLI, principal, recovery operation, permission, schema change or migration.** ADR-023's statement that emergency break-glass is not implemented remains factually true and is preserved; ADR-001 isolation remains in force.

[ADR-026 — Outbound Notification and Delivery Architecture](ADR-026-outbound-notification-delivery-architecture.md): **Accepted** (2026-10-04). Records transactional-outbox delivery intent, immutable per-notification Organization binding, structural `unique(organization_id, dedupe_key)` idempotency, a provider-neutral adapter registry with explicit delivery-reporting capability, and the required resident-safe content boundary. MVP is transactional resident email for system-generated lifecycle events; correspondence delivery, SMS and subscriptions are later or separately gated. Only Slice 1 is implemented — contracts, empty registry, resident-safe projection, code-based platform templates and a pure renderer. **Acceptance does not authorize live egress, provider integration, secrets, migrations, webhooks or deployment.** ADR-008 correspondence immutability remains in force; ADR-010's current no-external-delivery implementation state is amended as future architecture only.

[ADR-025 — Trusted Production Organization Resolution](ADR-025-trusted-production-organization-resolution.md): **Accepted** (2026-10-04). Records the approved `getreqro.com` product domain, verified customer resident domains, platform fallback hostnames and `public_canonical`/`public_alias`/`platform_fallback` roles; approves hostname-based anonymous tenant resolution and rejects path-based tenancy. Only the Slice 0 configuration boundary is implemented: `TENANT_RESOLUTION_STRATEGY`, removal of the hardcoded fixture Organization default, and production/client guards. Acceptance is not implementation: no registry, resolver, request context or schema exists, and each remaining part needs its own reviewed slice. It refines only the anonymous resolution that ADR-001 left open; ADR-001's isolation principles, identity-derived staff Organization and deployment-per-tenant preference remain in force, and shared SaaS stays separately gated.

[ADR-028 — Trusted Production Operator Execution](ADR-028-trusted-production-operator-execution.md): **Accepted** (2026-10-09). Records how a production tenant-domain operator invocation becomes trusted: inputs split into infrastructure-injected trusted execution metadata and human-selectable operation inputs, so humans choose the action and never the actor; `REQRO_OPERATOR_IDENTITY` refused in a serving environment; the recorded identity as the immutable IdP subject in the hyphenated form Migration 47 can store, with arbitrary OIDC `sub` values explicitly not claimed to be supported; five conceptual permissions on two independent axes, in which `tenant-domain.request` never authorizes `approve`, `tenant-domain.execute` is the distinct authority committing requires, `deployment.migrate` confers no control-plane change authority and `emergency.breakglass` is unimplemented and refused; just-in-time elevation bounded to 60 minutes and refused rather than trimmed when wider; provenance requiring both a full commit SHA and an immutable image digest; and a provider-neutral invocation audit trail that fails closed in serving. Runner trust is stated as a consistency check rather than an authentication, and immutable off-host audit retention is recorded as an open infrastructure blocker. Accepted means the Reqro trusted operator execution contract is accepted; it does **not** mean that Entra/PIM configuration, real OIDC federation, a protected production runner, immutable off-host audit retention, a production secret manager, production database authentication or a production network boundary exists — none does. **Nothing here authorizes a cloud resource, identity-provider group, PIM policy, CI workflow, federation, secret, production database user, grant change or deployment, and production deployment remains unauthorized.** It refines ADR-027 decision 10's infrastructure prerequisites into a checkable contract without moving that boundary; ADR-027's platform-authority and control-plane separation, ADR-025 hostname resolution and ADR-001 isolation all remain in force.

[ADR-029 — First Production Operator Platform](ADR-029-production-operator-platform.md): **Proposed, not Accepted.** Selects the first concrete implementation of the ADR-028 contract — GitHub source repository, Azure DevOps control plane, Microsoft Entra with PIM, a one-shot Azure Container Instance in a private VNet, managed-identity token authentication to Azure Database for PostgreSQL Flexible Server — while leaving ADR-028 and the provider-neutral `TrustedIdentityAdapter`, `OperatorAuditSink` and `TrustedRunnerAssertion` seams intact. Source control does not move; GitHub Actions is recorded as a supported alternate future control plane if GitHub Enterprise Cloud with Entra SAML/SCIM is adopted, and a hardened administrative runner is emergency/break-fix only. An Azure DevOps identity is explicitly **not** an Entra object ID: the acting human is resolved through Azure DevOps Graph, required to have `aad` origin in the expected tenant, and recorded as the immutable `oid`, with UPN, mail and display name non-authoritative. It also records the requester-attribution fix — a trusted request artifact, digest-bound through the trusted execution channel, from which an approval derives the requester instead of accepting a human-supplied one — the separate `dns-verification` and `restricted` execution network profiles that scope outbound DNS to the `verify` verb alone, and client-configurable audit retention with a two-year documentation baseline. **Nothing here authorizes an Azure DevOps organization, service connection, Entra group, PIM policy, federated credential, managed identity, PostgreSQL server, container instance, registry, network, storage, vault, secret or deployment; no migration is added and no database grant changes; production deployment remains unauthorized.**
