# ADR-009 — Secure requester tracking

**Status: Accepted** — F044 implementation decision; release validation and live UAT remain separate gates in the [feature record](../../features/F044-secure-requester-tracking-foundation.md).

**Amended by F065** — automatic requester-intake issuance and credential expiry. The amendment is applied inline below and summarised in [F065 amendment](#f065-amendment-automatic-requester-intake-issuance-and-expiry); the original F044 reasoning is otherwise preserved. The amended behavior ships disabled: see the activation prerequisites in that section and in the [F065 feature record](../../features/F065-public-submission-tracking-confirmation.md).

## Context

Request UUIDs and human references identify records; neither authorizes requester access. The workforce Entra/RBAC boundary cannot serve anonymous requester tracking. F042 correspondence remains separate and is not exposed by this foundation.

## Decision

Use a separate, cryptographically random 32-byte (256-bit), unpadded base64url bearer credential. Store only its SHA-256 hexadecimal digest in `request_tracking_credential`. This fast deterministic digest is suitable because the input is uniformly random with high entropy; it is not password hashing. Database disclosure alone cannot reconstruct usable links by practical exhaustive guessing, but still exposes any other data in the database and does not protect a compromised application/server.

Management requires normal PUBLIC parent read, current Organization/scope, trusted staff identity and `service_request.tracking.manage`. No default grants and no INTERNAL credentials. Migration issues nothing. Management GET returns safe status and an opaque concurrency version, never a digest or recoverable link. The UI keeps state discovery inside an explicitly opened F043 dialog.

F065 amends this: a credential is issued automatically for a PUBLIC Service Request at successful resident intake, inside the authorizing request-creation transaction, so request, credential and audit commit together or not at all. Automatic issuance is reachable only from that transaction. No HTTP route issues a credential for an arbitrary existing request, no permission key is added, no existing grant is widened, and staff intake and the trusted provider path are excluded. Issuance records an explicit `issuer_type` of `requester_intake` with no staff identity attributed, rather than fabricating a staff author. Subsequent management — rotation and revocation — remains staff-only under `service_request.tracking.manage` and is otherwise unchanged. Possession of an intake-issued credential is request-scoped access, not proof of personal identity. Automatic issuance does not weaken the PUBLIC/INTERNAL separation: the insert trigger PUBLIC-parent requirement, the `audience='public'` predicate in the digest lookup and the post-lock recheck all remain and apply identically to both issuer types.

One active credential per request is enforced by a partial unique index. Revoked rows remain; digest, request, Organization, author, issuer type, expiry and creation timestamp are immutable. Expiry is a stored timestamp evaluated as a predicate, not a stored status: an expired credential keeps `status='active'` and simply stops resolving, so the active-to-revoked transition and the one-active-credential index are untouched and no background expiry job exists. Because every new PUBLIC request therefore holds an active credential from creation, the normal staff action becomes rotation; initial issuance remains reachable only after a revocation. Only active-to-revoked state transition is allowed. Parent-first locking serializes management and authorized reads. Expected management versions reject stale/double-click operations. Issue/rotation/revocation and mandatory metadata-only security audit share a transaction. Audit failure rolls everything back. No parent operational data or revision changes.

Use `/track#<credential>`, consume and scrub the fragment before React Router construction, and send the secret only in `X-Requester-Tracking` to GET `/api/v1/requester-tracking`. This header is distinct from workforce Authorization. No caller-supplied Organization, UUID, audience or reference can select the authorized parent. Indexed digest lookup supplies the trusted pair; active credential, active Organization and persisted PUBLIC audience are rechecked with consistent locking before projection.

An explicit query/projection returns reference, versioned Issue name/icon, normalized status, submittedAt, entered service location and original description. Open remains Open; In Progress and On Hold become In Progress; Closed and Cancelled retain their safe labels. Unknown status becomes Unavailable. No operational narrative, contact, staff identity, UUID, revision, scope, Notes, Activity, assignment, watchers, capabilities or correspondence is included. Plain text is escaped; icons use the existing finite UI vocabulary. Field-level location/description sensitivity may need future client policy.

## Privacy and residual risks

Tracking/management API responses including denial and throttling use no-store, no-referrer and noindex. The frontend establishes no-referrer before scripts/assets and uses bundled assets. The tracking document has noindex metadata and a separate requester shell. The static hosting configuration already applies no-store to HTML. No new CSP relaxation is introduced. Existing global in-process API throttling applies; distributed limits/proxy configuration remain production requirements.

Raw values live only in issuance responses and temporary browser/server memory. Staff dialog close, request/access changes and requester-page departure clear application references. Refresh of a scrubbed page requires the original link again. This limits retention rather than promising JavaScript memory zeroization. No credential goes to application storage, title, analytics, audit or structured logs. Reverse proxies must not log the custom credential header. TLS is required outside approved localhost development.

Possession authorizes access; it does **not** verify a specific human's identity. Screenshots, clipboard history, extensions, browser synchronization and forwarding can disclose a usable link. Browser URL replacement cannot revoke copies already made. Narrow projection, rotation and revocation limit consequences. Already disclosed information cannot be recalled. F065 amends the expiry position: credentials issued once that feature is enabled expire. Lifetime is bounded by a platform policy of 30 to 365 days, defaults to 180 days, and is configurable per tenant within that bound through `request_tracking_policy`; the database CHECK means no tenant value can exceed the platform maximum even by direct SQL. Lifetime is fixed at issuance from the policy then in force and is never changed retroactively, because extending a stored expiry would resurrect a dead bearer credential and shortening one would revoke access with no audit record. Rotation issues a fresh lifetime and is the sanctioned renewal path. Credentials issued before this amendment have no expiry and keep none; no expiry is backfilled onto them, since that would be a retroactive mass revocation, and the resulting asymmetry is a recorded inconsistency for a later reviewed decision. Expiry is evaluated in SQL against the database clock in the same locked queries that validate the digest, never against application time. Expired, revoked and unknown credentials are all indistinguishable to a caller. Stronger accounts/OTP/CIAM, delegated/multiple requester access, delivery, tracking history and correspondence display are deferred.

## F065 amendment: automatic requester-intake issuance and expiry

F065 authorizes automatic issuance at successful PUBLIC resident intake, an explicit `requester_intake` issuer classification with nullable staff attribution, and immutable credential expiry under a bounded tenant policy. Digest-only storage, the one-active-credential rule, credential immutability, PUBLIC-only parents, staff-only rotation and revocation, and possession-is-not-identity are all preserved unchanged.

The capability ships **disabled**. `REQRO_ENABLE_REQUESTER_INTAKE_TRACKING` is OFF unless the environment says exactly `true`, so a missing or unrecognized value never activates it; there is no client override and no tenant bypass, and applying the migration does not switch it on. While disabled, PUBLIC submissions return exactly the receipt they returned before and staff issuance stays non-expiring.

Activation is gated on a known weakness rather than on readiness alone. Submission idempotency today covers only submissions carrying attachments, keyed on the attachment batch and a content digest; an attachment-free submission retried after a lost response creates a second request, and with automatic issuance it would also mint a second credential. This is pre-existing behavior that F065 makes more consequential, and it is the reason the feature is gated. The system is not represented as having complete submission idempotency.

Activation prerequisites, all separately approved:

1. All-submission idempotency implemented and validated. Implemented by [F066](../../features/F066-all-submission-idempotency.md) under [ADR-031](ADR-031-submission-idempotency.md); this prerequisite remains **open** pending independent validation of that implementation.
2. Migration safely applied under separate authorization.
3. Credential lifecycle and recovery support accepted, noting that the raw credential is unrecoverable from its digest and that rotation by staff is the only replacement path.
4. Security regression tests passed.
5. Non-production rollout approved.
6. Explicit feature activation approved.

Deployment ordering matters: the migration must precede the application code, because code that writes `issuer_type` against the pre-F065 schema would fail inside the request-creation transaction and take PUBLIC submission down with it. The rollback window closes at the first intake issuance, because `down()` fails closed rather than converting a requester-issued credential into a staff-issued one, removing an expiry or deleting credentials to make itself pass.

## Operational consequences

Network-loss after successful issuance may lose the only raw copy. There is no secret recovery or automatic replay; reopen state and deliberately rotate after confirmation. New management requires a reviewed current version. Safe rollback is allowed before meaningful tracking state/audit/grants and refused afterward. Live development UAT ends revoked so no usable secret needs retaining for the next feature.
