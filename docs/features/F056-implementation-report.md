Read-only administrators see configuration without mutation controls. Labels describe requester policy and assignment in human terms. No autosave, optimistic revision advancement, arbitrary HTML, adjacent swaps, Category restructuring, form designer, action editor or bulk update.

No DELETE or generic configuration mutator. Strict DTO/domain validation rejects unknown/forged fields and invalid nested targets. Trusted active Organization/staff context comes from server authorization. Cross-Organization Issue IDs are indistinguishable from unavailable IDs. Targets use F048 eligibility and safe labels; operational membership does not grant administrative or request authority. Registration and bundles provide zero default Issue-write grants. Responses are no-store. Missing authentication, missing authority, unavailable resource, stale configuration and invalid input remain distinct 401/403/404/409/400 responses. Duplicate names receive the fixed safe message “An Issue with this name already exists.”

## Identity, revisions, templates and history

Stable UUID/service-key identity is retained. Every Save checks all four expected revisions under the stable Issue lock. The core revision covers current immutable version pointer, active state and order; action, policy and assignment remain separate domains. F048/F049 changes and their audits participate in the same transaction. Only changed resources advance. No-op and rejected operations leave revisions, state, history and successful mutation audits unchanged. Audit failure rolls everything back.

Existing Issues start at core revision 1 and order 0. A new Issue is inserted inactive at core revision 1 and publication of its initial version advances core to 2 inside the same atomic create transaction. The response returns that actual revision; the UI does not assume 1. Policy starts at 1 after explicit initialization; assignment remains 0 for None or becomes 1 for a selected target; action starts at 1. Initial catalog version is 1. Internal published-version status means immutable complete catalog content, not active intake availability. Explicit activation remains required. This clarifies original §275 question 25 under the approved template/immutable-version design.

Creation explicitly copies the template's Category and mandatory icon/priority/location/geographic/form configuration with fresh stable/version/question/option IDs and preserved form keys. Optional aliases, keywords and routing metadata are not silently inherited for a new resource. Requester policy and default assignment use explicit form values. Later template edits cannot propagate. Rename/description edits preserve the existing Issue's remaining versioned configuration in a new immutable version; historical requests retain their stored version. No request or historical form/reference is rewritten.

Current names use PostgreSQL trimmed lowercase comparison within Organization, across active and inactive Issues; display capitalization is retained. Current-name cache is database-derived from the selected version and protected by an expression unique index. Historical version names are outside this namespace. Existing service-key uniqueness remains. Unicode boundary trimming matches the F055 convention; no accent folding, transliteration or internal-space normalization. Retired names are reserved for reactivation.

Order is nonnegative integer up to 2147483647, with valid ties. Category grouping is preserved; within each Category, display order, display name and stable ID determine order. No normalization or rewrite of existing order values. Deactivation preserves existing requests/assignments and blocks all new creation paths through both catalog selection and a current active-state check under the creation lock. Finalized attachment retries retain their existing return-original behavior.

## Audit, privacy and threat review

F056 immutable audit contains Organization, internal actor, stable Issue, action, changed field names, prior/resulting core revision, resulting policy/assignment revisions, correlation and timestamp. F048/F049 retain separate domain audits. Reads and no-op writes do not create change audit noise. Database triggers reject audit update/delete/truncate; rollback refuses retained configuration, audits or grants.

Threats tested: missing or unrelated grants; forged Organization/fields/revisions/target types; real foreign Issue/template/target identifiers; case/whitespace duplicate races; inactive name reuse; stale writes; same-Issue concurrent saves; independent-Issue saves; audit/validation failure halfway through transaction; stale anonymous policy; deactivation between pre-validation and locked creation. Database constraints supplement API validation. React renders names/descriptions as text, and error responses do not serialize arbitrary exceptions. New grants confer no operational, Contact, Notes, Communication, attachment, tracking, requester-history, analytics or geospatial access.

Normal log tests exclude mutation payloads, descriptions and provider identity. The user confirmed PASS for live denied/success/conflict logging privacy on 2026-09-24. No token copying, credential export or tracking operation is part of UAT. The integrity helper excludes tracking digests entirely and stores only hashes of existing rows in ignored local scratch storage.

## Performance and limits

Admin list uses a fixed count query and a joined 25-row projection in one read-only repeatable-read transaction; no per-row fetch/history scan or React filtering of foreign data. Target search is bounded to 100 characters and existing F048 limits of 25 results per type/audience, with at most six queries and deduplication. Template version/form copying uses set-based SQL. Stable Issue locks serialize competing writes to the same Issue and request creation; different Issues can update independently. Organization lock is shared, not a global revision/write mutex. Unique index arbitrates competing logical names in PostgreSQL.

The editor offers valid templates from its current page and explains this; administrators can page before starting creation. Page count and independent fetches are not one catalog-wide snapshot. Eligibility can change independently of the configuration revisions and is therefore revalidated. No production-scale/load benchmark or accessibility certification is claimed. Existing frontend large-chunk advisory remains.
